PayFlow — Distributed Digital Wallet & Payment System

A distributed digital wallet system handling concurrent financial transactions across 3 independent microservices. Built with Java 17, Spring Boot 3 and an event-driven architecture via RabbitMQ. Engineered to prevent race conditions, double-spending and database deadlocks under heavy load.

Microservices Architecture

Three independently deployable services communicating via RabbitMQ events

Auth Service

Handles user registration, login and token issuance. Implements Spring Security with JWT-based stateless authentication and BCrypt-hashed credentials. Acts as the entry point that other services trust via signed tokens.

Spring Security JWT BCrypt MySQL

Wallet Service

The financial core — manages account balances, deposits, withdrawals and peer-to-peer transfers. Uses pessimistic row-level locking and idempotency keys to guarantee correctness under concurrent load. Publishes transaction events to RabbitMQ.

Hibernate Pessimistic Locking Idempotency RabbitMQ Producer

Notification Service

Asynchronous consumer of transaction events from RabbitMQ. Decouples user-facing notifications from the transaction critical path so wallet operations never block on email or alerting infrastructure.

RabbitMQ Consumer Spring AMQP Event-Driven

Transaction Flow

How a money transfer flows through the system end-to-end

1

Authenticate

Client presents JWT issued by Auth Service. Wallet Service validates the token signature.

2

Idempotency Check

Each transfer carries a unique idempotency key. Duplicate retries return the original result safely.

3

Lock & Validate

Pessimistic lock on sender + receiver rows in a deterministic order to avoid deadlocks. Balance and limits checked.

4

Atomic Debit + Credit

Both sides updated within a single database transaction. Either both succeed or neither — no partial state.

5

Publish Event

Successful transaction published to RabbitMQ. Wallet Service responds to client immediately.

6

Notify Async

Notification Service consumes the event and dispatches alerts independently of the transaction path.

Engineering Highlights

The hard parts that make this production-grade rather than a tutorial

Pessimistic Locking

Row-level locks on wallet records during transfers prevent two concurrent transactions from reading the same balance.

Idempotent Transactions

Every transfer accepts a client-supplied idempotency key. Network retries and duplicate clicks never debit twice.

Deadlock Prevention

Locks acquired in a deterministic order (lower account ID first) so two simultaneous reverse transfers cannot deadlock.

Double-Spend Protection

Balance check and debit happen inside the locked transaction. There is no window where stale balance can be acted on.

Event-Driven Notifications

Transaction path never blocks on alerting. RabbitMQ decouples slow notification work from the user-facing critical path.

JWT + BCrypt Security

Stateless auth via signed JWTs. Passwords hashed with BCrypt — never stored or logged in plaintext.

Daily Transfer Limits

Per-user daily caps enforced at the service layer with rolling windows — adjustable per account tier.

60+ Test Cases

JUnit 5 + Mockito coverage including concurrent transfer simulations and failure-injection scenarios.

Containerized Stack

Every service plus MySQL and RabbitMQ runs via a single docker-compose up — reproducible across machines.
